# Disaster Recovery

**Status: DEPRECATED.** Written for the pre-Titan-Protocol
`phantom_pipeline/deployment/` package's `backup_manager.py`/
`logging_manager.py`, which the current Titan Protocol Windows release
(`deployment_windows/`) does not use. See
`deployment_windows/WINDOWS_OPERATOR_GUIDE.md`'s "Rollback" section for
the current release's much simpler backup/removal story. Kept for
historical reference only.

Backup, restore, and incident-response reference for a production Phantom
deployment, built on `phantom_pipeline/deployment/backup_manager.py` and
`logging_manager.py`.

## 1. What is backed up

| Target | Mechanism | Source |
|---|---|---|
| Configuration | checksummed file copy | profile config files (`C:\phantom\config\`) |
| Databases | `sqlite3` online backup API (never a raw file copy of a live DB) | any SQLite-backed store (e.g. Watchdog/Compliance state stores, if configured to persist) |
| Analytics | checksummed file copy | `AnalyticsEngine`'s persisted provenance records, if exported to disk |
| Trade history | checksummed file copy | exported trade/provenance history files |

Every backup is SHA-256 checksummed at creation
(`BackupManager._sha256_of_file`), and the checksum is stored alongside
the backup in a `BackupRecord`, never recomputed from the live source at
restore time — restore always trusts the backup's own recorded checksum,
so a backup silently corrupted after creation is caught before it is
ever restored (`BackupManager.restore` refuses on mismatch).

## 2. Backup schedule (operator-configured; this package provides the
mechanism, not the scheduler)

Recommended minimum: daily full backup of all four targets, retained per
`enforce_retention_policy`'s configured `retention_days` (align this with
your prop firm's own audit-retention requirement, not just convenience —
`docs/adr/` and `VALIDATION_MATRIX.md` do not set this value, it is an
operator decision).

## 3. Verifying a backup

```python
manager = BackupManager(backup_root)
assert manager.verify_integrity(record)  # re-hashes the backup file itself
```

Run this on a schedule, not only at restore time — an unreadable or
corrupted backup should be discovered while there is still time to take
a fresh one, not during an actual incident.

## 4. Restore procedure

1. Stop the affected service via `ProductionDeploymentManager.stop_all`
   (or the single affected `ServiceDefinition.stop`) — never restore a
   file a running process still has open.
2. `manager.restore(record, destination, now)` — refuses automatically
   on any checksum mismatch, before or after the copy.
3. Restart via `ProductionDeploymentManager.start_all` and confirm
   `DeploymentValidator.run(...)` reports `all_passed` before resuming
   live trading.

## 5. Incident scenarios

- **MT5 terminal crash mid-session**: `WindowsServiceManager.
  check_and_restart_crashed` restarts it automatically — unless a trade
  is actively executing (`trade_in_progress` probe), in which case the
  restart is deferred and logged, never silently attempted against a
  live order. Manually verify no order is stuck once the position is no
  longer active, then let the next scheduled check restart it.
- **VPS reboot**: `WindowsServiceManager.ensure_started_after_reboot`
  brings every registered service back in dependency order (via
  `ProductionDeploymentManager`'s topological ordering).
- **Corrupted SQLite database**: restore the most recent verified backup
  via §4; the online-backup mechanism means the backup itself was never
  torn mid-write, so restoring it is safe even if the corruption
  happened live.
- **Full VPS loss**: provision a fresh VPS per `VPS_SETUP_GUIDE.md`,
  restore configuration + databases + trade history from the last
  verified backup set, re-run `DeploymentValidator` before resuming.
- **Crash with no clean shutdown**: check `crash_dumps/` for a structured
  JSON dump (`generate_crash_dump`'s output — component, exception type,
  full traceback, caller-supplied context) generated by whatever
  component's own exception handler called it; this is the first
  artifact to attach to any incident review, before trawling raw logs.

## 6. What this package does **not** do

- It does not automatically fail over to a second VPS — this is a
  single-instance deployment package. Multi-region failover is out of
  scope for Phase 5 and would need its own RPI cycle.
- It does not encrypt backups at rest. If your prop firm's data-handling
  policy requires encryption, add it at the filesystem/volume level
  (e.g. BitLocker) — this package's own checksum guarantees integrity,
  not confidentiality.
